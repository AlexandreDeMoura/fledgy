# Fledgy's web view inside Codex desktop

Researched 2026-11-05. Documentation and source inspection only; no UI verification or implementation.

**Use the built-in browser first.** Official documentation explicitly supports local web apps beside a Codex conversation. Fledgy's existing server already supplies the page and its data together, so no data adaptation appears necessary for that route. A dedicated plugin page or conversation panel is a separate integration, with additional work and an unresolved compatibility question. [Browser documentation](https://learn.chatgpt.com/docs/browser), [current server](../../src/view.ts#L54).

| Option | What is established | Fledgy work |
| --- | --- | --- |
| Open the localhost URL in the built-in browser | The desktop browser supports local web apps, full view and split view. Its documentation explicitly names Codex and gives a localhost example. | Start the existing server and open its URL. No transport change expected; this is an inference from Fledgy's current code. |
| Add a dedicated plugin page or panel | OpenAI documents MCP App global sidebar and thread panel entrypoints for ChatGPT. Codex supports plugins. These sources do not explicitly establish that arbitrary third-party **local** MCP Apps receive both entrypoints in every Codex desktop version. | Confirm that exact capability in the target desktop version before implementation; then add MCP registration, UI packaging and data access. |

Sources: [browser](https://learn.chatgpt.com/docs/browser), [plugin entrypoints](https://developers.openai.com/plugins/build/extensions), [supported plugin surfaces](https://learn.chatgpt.com/docs/plugins), [Fledgy server](../../src/view.ts#L61).

The current documentation calls the host the **ChatGPT desktop app**, with Codex available inside it. That is the documented product scope here; it does not prove identical behavior in an older standalone Codex desktop release. [Plugin surfaces](https://learn.chatgpt.com/docs/plugins), [Codex browser support](https://learn.chatgpt.com/docs/browser#computer-use-in-the-browser).

For the browser option, run `git fledgy view` from the app repository, keep that process running, then open `http://localhost:4173/` in a desktop browser tab. The CLI finds the Git repository root, starts the server on port 4173 by default and prints its URL; it does not launch a browser itself. In the desktop app, use **New tab** or **Cmd+T**, enter the URL and choose split view to keep chat beside it. [Fledgy command](../../README.md#L37), [CLI root selection](../../src/cli.ts#L15), [server command](../../src/cli.ts#L32), [desktop browser controls](https://learn.chatgpt.com/docs/browser).

“Adapt how the view gets data” applies only if the view becomes an MCP App resource. Today `refresh()` fetches `/api/data`; `post()` sends JSON to `/api/result`, `/api/note` and `/api/result-reset`. The server returns the Knowledge base, code changes and QA Results, and writes QA Results on the Builder's computer. Those relative URLs work because the page and API share the localhost origin. [Reads](../../view/view.js#L1103), [writes](../../view/view.js#L174), [write callers](../../view/view.js#L844), [server responses](../../src/view.ts#L67), [QA Result handling](../../src/view.ts#L113).

For an MCP App integration, the concrete changes would be:

1. **Register and package the UI.** Add an MCP server, an HTML resource and a tool declaring `_meta.ui.resourceUri`. Initialize the MCP Apps bridge. Plain HTML, CSS and JavaScript can remain; adopting React is unnecessary. Existing `/view.js`, `/view.css` and `/themes.css` asset URLs would need bundling, inlining or explicit permitted asset URLs. [MCP UI guide](https://developers.openai.com/plugins/build/chatgpt-ui), [current HTML](../../view/index.html#L1).
2. **Replace the HTTP calls, if choosing bridge-based access.** Keep the same response shape for `DATA`; route the existing read, record, note and reset operations through MCP `tools/call` and tool results. Reuse the current server's Knowledge base reading, change calculation and QA Result logic behind those tools. This is an implementation proposal, not a requirement to change Fledgy's file formats or rewrite its screen. [Bridge mapping](https://developers.openai.com/plugins/build/chatgpt-ui#prefer-shared-fields-and-methods), [current API operations](../../src/view.ts#L61), [current view state](../../view/view.js#L17).
3. **Bind the app repository explicitly.** The current HTTP process captures `repoRoot` at launch. A packaged local MCP process must receive or select the intended repository/worktree too; its package directory is not the app repository. Preserve the Builder's home-based QA Results. Do not assume sidebar selection automatically supplies a repository path: the cited entrypoint guide does not promise that. [Current binding](../../src/cli.ts#L15), [server arguments](../../src/view.ts#L54), [local MCP launch example](https://developers.openai.com/plugins/deploy/desktop-only#configure-a-local-mcp-server).
4. **Preserve refresh behavior deliberately.** The view rereads on load and window focus, skipping refresh while a note is being typed; the server rereads files on every API request. There is no file-change subscription. A panel could retain a refresh action and requery its data tool; automatic updates would need an added mechanism. Knowledge base edits do not require republishing the UI resource. Resource caching/versioning concerns HTML/JavaScript/CSS changes instead. [Current refresh](../../view/view.js#L1100), [server rereads](../../src/view.ts#L54), [resource caching](https://developers.openai.com/plugins/build/chatgpt-ui#register-the-ui-resource).

A bridge rewrite is **not the only possible design**. MCP UI policy allows declared API connections and, with restrictions, embedding an existing page in a nested iframe. That does not establish that `http://localhost:4173` is accepted in either position: nested frames are blocked by default, iframe origins require declarations, and the published policy focuses on the MCP server's own registrable domain and review. A localhost wrapper remains a compatibility question, not a documented shortcut. [CSP reference](https://developers.openai.com/plugins/reference), [iframe policy](https://developers.openai.com/plugins/plugin-guidelines#iframes-and-embedded-pages).

The UI also uses browser history, clipboard access and `vscode://` Anchors. These are additional host-sensitive behaviors to account for in an MCP App; the sources do not establish that they work unchanged in its sandbox. [Navigation](../../view/view.js#L21), [clipboard](../../view/view.js#L1006), [Anchors](../../view/view.js#L606), [MCP iframe runtime](https://developers.openai.com/plugins/build/chatgpt-ui).

Private experimentation and public distribution have different constraints. OpenAI documents local/repository marketplaces for authoring and private distribution, plus local stdio MCP packaging. Public local MCP submissions are currently limited to approved partners with allowlisted organizations; desktop-only plugins can be mentioned only in locally running threads. These restrictions do not prevent using the existing localhost view in the desktop browser. [Local marketplaces](https://developers.openai.com/plugins/build/plugins#how-local-marketplaces-work), [desktop-only submission](https://developers.openai.com/plugins/deploy/desktop-only).

**Decision:** displaying Fledgy inside the documented desktop browser needs no planned rewrite. Pursue an MCP App only if a dedicated plugin page/panel or chat integration is valuable enough to justify it. Exact third-party local MCP App entrypoint support, localhost iframe allowance and sandbox behavior remain unverified; the Builder should manually assess those before committing to that integration.
